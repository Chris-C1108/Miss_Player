## 🎯 核心问题与设计反思

### 1. 响应式布局优化时“防止过度干预子微件尺寸”的教训
- **反思**：在治理容器最大宽度失控（父级宽度过宽）时，不应盲目通过在媒体查询中对子微件（如 `.tm-time-control-button`）添加全局 `!important` 强制压缩高度（从 40px 砍到 28px）和圆角。这种激进的“削足适履”做法虽然强行把按钮塞进了一行，但却严重破坏了按钮原本成熟饱满的视觉比例和舒适的触控热区。
- **正解**：宽度约束应聚焦在父级容器的容器宽度模型（`max-width: 480px; width: calc(100vw - 24px)`），子微件应保持其核心的高度、内边距与圆角设计语言不变。

### 2. 官方 API 与 CDN 备用源在反爬对抗下的双轨冗余设计
- **教训**：直接依赖各大脚本托管平台（如 SleazyFork / GreasyFork）的前台 JSON API 极易被其边缘节点（如 Cloudflare Turnstile / 5秒盾）误伤判定为 403 爬虫。
- **最佳实践**：必须建立双轨容错机制。前台 JSON API 优先获取完整社区指标（安装量、评分等）；一旦遭遇 403 或拦截，立即无感降级到官方专门用于脚本自动更新的直链 CDN（如 `update.sleazyfork.org/...meta.js`）进行版本正则提取，保证用户的核心升级链路 100% 畅通。
