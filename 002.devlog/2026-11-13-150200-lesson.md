# Lesson Learned: 杜绝过度设计与过度归因，直击样式层直接表现 (2026-11-13)

## 1. 警惕过度归因与复杂度膨胀 (Avoid Over-Attributing UI Margin Issues)
- **现象**：当用户截图指出“评论区底部不需要边距”并圈出底部空白时，Agent 一度陷入了包含 `UIManager.js`、`_layout.css`、`_single_hand.css`、`visualViewport`、flex column 子元素高度算力等一连串宏观生命周期排查，甚至尝试裁图分析色彩直方图。
- **反思**：在单页面 UI 框架中，一个明显的下沿留白往往就是样式表中硬编码的 `padding-bottom` 或 `margin-bottom` 所致。
- **FORBIDDEN**: 在面对直观的边距/留白反馈时，盲目怀疑底层状态机或执行过度侵入式的跨组件审查。
- **USE**: 优先检查目标容器与其直接子元素的 `padding`、`margin` 与 `box-sizing`，保持奥卡姆剃刀原则，以最小改动直击痛点。

## 2. 滚动容器嵌套底部内边距双重叠加陷阱
- **反模式**：在外层滚动容器 `.tm-comments-list` 设置了 `padding-bottom: 24px` 的同时，又在其内部的每个 `.tm-comment-section-body` 设置了 `padding-bottom: 24px`。
- **后果**：在仅有一个 section 或滚动到底部时，内外部内边距叠加产生近 50px 的死留白，给用户造成“列表断流”或“空白屏”的视觉误解。
- **最佳实践**：纯流式列表统一将内边距交由子项自身的呼吸感（如 `padding: 13px 16px`）负责，容器级一律保持 `padding: 0;`。
