# 经验教训沉淀 (Lesson Learned) - 2026-11-11-182800

## 1. dev 开发测试常驻工作区 + main 生产专有分支双轨架构落地

### 🚨 历史反模式与陷阱复盘
1. **测试版与正式版同分支竞争陷阱**：
   - 过去在 `main` 上既进行日常开发与真机调试，又作为正式版发版入口，导致频繁的 `-beta.xxx` 碎提交污染了正式版门面历史；
   - 依赖远程隐式 `release` 分支进行 Webhook 发版，使得开发者本地与远程拓扑脱节。
2. **测试通道分支死硬编码（幽灵失更）**：
   - `SleazyForkService.js` 中如果死锁为 `main` 分支拉取，一旦转为在 `dev` 上日常开发，手机端测试版将永远检测不到 `dev` 上的新提交，导致“已推送但手机端永远显示最新”的幽灵失更；
   - **USE: 测试版通道抓取源（`GITHUB_RAW_META_URL` 等）必须精准绑定为 `dev` 分支**。
3. **分支跨界覆盖破坏 Git 连贯性**：
   - FORBIDDEN: 随意执行本地分支切换、覆盖拷贝代码文件破坏 commit 历史 -> USE: 严格采用原子镜像快进直推 `git push origin dev:main`，本地常驻工作区分支始终锁定为 `dev`。

## 2. 构建系统动态分支与合规门禁自愈

1. **构建脚本自适应 Git 分支**：
   - `vite.config.mjs` 与 `webpack.config.js` 引入 `execSync('git rev-parse --abbrev-ref HEAD')`；
   - 处于 `main` 分支构建时自动注入指向 `main` 的 `@downloadURL` 与 `@updateURL`；
   - 处于 `dev` 分支构建时自动注入指向 `dev` 的 `@downloadURL` 与 `@updateURL`。
2. **合规门禁双分支放行**：
   - `scripts/compliance-lint.js` 升级为同时校验 `dev` 与 `main` 分支的合法 raw 直链，防止 CI 门禁误报阻断。
