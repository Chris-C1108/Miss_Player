## 🧠 核心技术陷阱与解决经验

### 1. HTML5 <video> 异步 Seeking 状态下的时间轴抖动与瞬间跳过陷阱
- **陷阱表现**：在回看或预览模式下，点击播放后进度疯狂跳跃，每个胶囊仅仅闪过 1 秒甚至更短就自动切到了下一个胶囊。
- **根因分析**：
  - 设置 `video.currentTime = startTime` 在现代浏览器中是**异步执行**的，视频元素并不会在当前执行栈中瞬间完成跳转；
  - 在底层解码器完成 seek 之前，浏览器会立即触发 `timeupdate` 事件，此时 `currentTime` 仍然停留在上一次的播放位置（例如 0 秒）；
  - 代码中直接使用了 `if (ct < startTime || ct >= endTime)` 的双向界限判定，导致在刚执行跳转的一瞬间，`ct < startTime` 必定命中，进而直接触发 `_capsulePlayIndex++` 切入下一胶囊，产生雪崩式连环跳。
- **正解实践**：
  1. **挂起异步 Seeking 锁**：跳转时标记 `_isSeekingCapsule = true`，监听视频原生的 `seeked` 事件，并在触发后额外留出 350ms 缓冲让播放头平稳推进后再释放锁；
  2. **消除反向超时判定**：将判断条件收敛为仅当时间真正越过终点（`ct >= startTime + duration`）时才跳下个胶囊；
  3. **保底时长防护**：回看模式下强制设置 `Math.max(15, endTime - startTime)` 保底播放 15 秒以上，单点时间戳播放 45~60 秒。

### 2. 免费层数据库下的存储物理开销：单行关系型 vs JSONB 压缩聚合
- **陷阱表现**：在 Supabase 500 MB 免费额度下，如果按照传统“1行=1条评论”设计，在每天 10,000 条评论的写入频率下，数据库将在大约 60 天左右因磁盘占满而触发只读锁定。
- **根因分析**：
  - Postgres 单行数据存在 Tuple Header（24 字节）与行填充开销；更致命的是**索引物理膨胀**：主键 B-tree、avcode 索引、hash_fingerprint 唯一索引加起来单行索引高达 160 字节，占了存储的将近一半；
  - 单条评论仅有 100~300 字节，无法触发 Postgres 的 TOAST 自动压缩机制，完全以裸文本存储。
- **正解实践（方案 1）**：
  - 重构为**“1行=1个番号的所有评论合集” (`video_comments_bundle`)**；
  - 仅保留 `avcode` 唯一样本主键索引，消除 99% 的索引物理开销；
  - 评论体合并后轻松突破 2 KB 阈值，底层透明激活 **TOAST LZ4/PGLZ 强力压缩**（压缩比 3:1 ~ 5:1）；
  - 单条评论折合成本从 0.8 KB 暴降至 60~90 字节，500 MB 额度可容纳超 500 万条评论，平稳支撑 1.5~2 年以上。

### 3. 爬虫跨站点路径特征盲区与初级正则贪婪导致的假阳性泛滥
- **陷阱表现**：在 MissAV 页面开启疯狂采集时，后台扫描出了大量形如 `DM-278`, `DM-539`, `DM-22086`, 以及 `SEP-2026` 的所谓候选番号，随后向 Jable 批量发起请求造成 90 次连续 404 刷屏。
- **根因分析**：
  - 爬虫直接在页面所有包含 `title` 或 `name` 类名的节点上执行了通配正则 `([a-zA-Z]{2,6})[-_\s]?(\d{2,5})`；
  - 英文更新日期 `Sep 2026` 被硬生生组合成了 `SEP-2026`；
  - MissAV 内部的样式类名或中文字幕企划（`dm-xxx`）被抓取出来，而 Jable 完全没有收录此类非日系标准番号；
  - 爬虫模块没有复用主库成熟的 `videoCode.js` 校验引擎，处于裸奔状态。
- **正解实践**：
  - 废除爬虫内部私有正则，强制接入 `videoCode.js` 的 `matchAvCodeFromText` 与 `isValidAvCode` 漏斗；
  - 在 `TECHNICAL_BLACKLIST` 中全量加入 12 个英文月份（`JAN` ~ `DEC`）及通用技术单位（`FPS`, `MB`, `VOL` 等）；
  - 针对外部爬虫严格跳过 `DM-xxx`，避免跨站无效 404。

### 4. WebDAV 空 Body PROPFIND 触发 415 假死与单文件并发死锁
- **陷阱表现**：WebDAV 客户端频繁报 `MKCOL 创建目录 ... 遇到状态码: 415`，同时所有番号全部往同一个 `miss_player_comments_debug.json` 中写入导致网络拥堵。
- **根因分析**：
  - 向部分 WebDAV 服务器（如 Nginx, Alist）发送空请求体的 PROPFIND 时携带了 `Content-Type: application/xml`，部分网关因无请求体却声明 XML 而返回 415，导致探测函数误以为目录不存在，进而发起多余的 MKCOL；
  - 单一大文件在频繁爬取时每次都要先读回全量历史 JSON 再写回，极易发生并发竞态覆盖。
- **正解实践**：
  - 空 Body 的 PROPFIND 去除 `Content-Type` 标头，并将 415 与 405、207 一并视为目录已就绪；
  - 彻底拆分为独立文件：按番号单独存放至 `/MissPlayer/comments/[AVCODE].json`，单次原子 `PUT` 极速写入，零网络往返冲突。

### 5. 视频元数据加载竞争与多层级时长提取漏斗
- **陷阱表现**：入库的 `duration_seconds` 经常为 0。
- **根因分析**：在页面启动时抓取评论，HTML5 `<video>` 尚未就绪，`video.duration` 为 `NaN`，转为整数后直接变成 0；稍后元数据加载完成触发 `reprocessComments` 时，仅更新了本地 DOM，未同步上报云端。
- **正解实践**：
  - 建立四层提取漏斗 `getVideoDurationSeconds()`：`video.duration` ➔ OpenGraph Meta 标签 ➔ 播放器 UI 文本 ➔ 页面面板文本，最大化提前命中时长；
  - 在 `loadedmetadata` 触发或 `readyState >= 1` 时，自动携带精确物理时长向云端 RPC 进行追写；
  - 服务端 RPC 使用 `case when excluded.duration_seconds > 0 then ... else existing end`，确保非零有效时长永远不会被覆盖为 0。

### 6. 静默抓取器中的变量作用域泄露 (ReferenceError)
- **陷阱表现**：控制台输出 `Can't find variable: currentUp`，导致后续代码被 catch 中断。
- **根因分析**：在单条爬取方法中直接引用了仅存在于外部扫描函数中的 `currentUpper`，触发 JavaScript 作用域未定义错误。
- **正解实践**：
  - 在模块方法内部保持纯净自包含，使用本地作用域变量获取当前播放番号，严格杜绝闭包外部未声明变量依赖。
