## 🎯 核心问题与架构踩坑记录

### 1. 外部代理开发脚本（@require）的 GM_* 沙箱断流陷阱
- **现象**：当本地通过 `vite-plugin-monkey` 生成的 `miss_player.proxy.user.js`（通过 `@require http://localhost:5173/miss_player.user.js` 加载）在浏览器执行时，代码内部无论如何调用 `typeof GM_xmlhttpRequest` 均返回 `undefined`，导致自动退回原生 `fetch` 并触发 CORS OPTIONS 预检失败。
- **根因**：Tampermonkey 的沙箱机制规定，虽然主脚本元数据声明了 `@grant GM_xmlhttpRequest`，但这些 API 只会注入给主脚本本身的沙箱作用域。若代理脚本只有 Header 声明而没有代码体，被 `@require` 引入的外部脚本并不能自动继承局部变量形式的 GM API。
- **解决方案**：在 `dist/miss_player.proxy.user.js` 构建后置处理中，自动注入一段将沙箱内 GM API 显式赋值给 `window` 和 `globalThis` 的桥接函数体，彻底打通外部代理调试脚本的特权调用链路。

### 2. WebDAV 预检重定向 (OPTIONS 302/307 Redirect) 与同源策略死锁
- **现象**：飞牛私有云（fnOS）等具备路径自动重定向或 HTTPS 规范化的 WebDAV 服务，在浏览器原生 `fetch` 发送自定义 Header 时会触发 CORS OPTIONS 预检。W3C 规范严厉禁止预检请求发生重定向，导致直接触发 `net::ERR_FAILED`。
- **解决准则**：WebDAV 客户端必须建立多级 GM 特权网桥（`GM_xmlhttpRequest` ➔ `GM.xmlHttpRequest` ➔ `window.GM_xmlhttpRequest`），无条件优先走扩展特权网络，完全绕过浏览器预检与 CORS 拦截，并原生安全支持 302 跳转。

### 3. 微件交互心智与空间占用治理
- **教训**：在设计设置面板时，不应盲目为了“交互感”塞入不必要的三段式切换胶囊（如主播放按钮默认当然是常规连播），而是将空间让位给用户真正需要配置的数值（如快速预览与精彩重温的播放时长）。
- **空间节约**：重型表单（WebDAV、关于与版本更新）必须采用手风琴折叠（Accordion），默认只呈现 40px 高度的状态指示行，避免面板垂直高度过度膨胀，保障单手操作视口紧凑利落。
