## 🎯 核心问题与设计反思

### 1. 样式重构先后时序的“Token 惩罚陷阱” (Refactoring Order Inversion)
- **现象**：按常规思路先从 JS 业务组件中“拔除牛皮癣（提取内联样式）”，看似直观，但在巨石架构下会导致严重的 Token 膨胀。
- **根因**：
  - 核心样式文件（如 `_player.css`）原本高达 3,002 行，如果先提取内联样式，Subagent 每次读写都要加载整整 3,000 行上下文，不仅 Token 开销极大，且无法使用尚未建立的 Tokens 标尺；
  - 提取完样式后，到下一步拆分目录结构时，又必须把刚刚追加进巨石文件的代码再次剪切并迁移到新文件，造成严重的“二次修改（Double Work）”与 Diff 冲突。
- **最佳实践**：
  - **必须遵循“先立宪 ➔ 先建基建 Tokens ➔ 先拆分大文件为微组件 ➔ 再提取内联样式”的反向顺序**；
  - 先将 3,000 行巨石拆解为 400 行左右的高内聚微组件（如 `_marker_sheet.css`），后续治理 `MarkerBottomSheet.js` 时读写上下文直接缩小 80%，且提取的类名能够“一步到位”直接引用规范变量。

### 2. 两代横屏引擎互掐的历史技术债务 (`_landscape_legacy.css` vs `_landscape_pc.css`)
- **现象**：CSS 文件中充斥着数百个 `!important`，排查发现是由于移动端横屏样式和桌面端横屏样式在同一个视口下暴力抢夺特异度。
- **根因**：
  - 历史演进中引入了新版 Grid 响应式文件 `_landscape_pc.css`，但未将旧版 `_landscape_legacy.css` 彻底退役，导致两者在 `style.css` 中同时被加载；
  - 进一步排查发现，旧版中的选择器（如 `.tm-video-overlay.controls-hidden .tm-button-container`）在现代 DOM 树中早已不存在，属于命中率为 0% 的“幽灵代码”，却一直在浪费特异度。
- **最佳实践**：
  - 引入新架构文件时，严禁与旧文件“叠罗汉”；
  - 建立选择器逐条比对矩阵，提取旧文件中真正有价值的“黄金规则”（如 iPhone 矮屏 480px 排版压缩和安全区避让），合入新版文件后彻底删除旧文件。

### 3. 设置面板旧代码的“假死判据”踩坑 (False-Dead Code Hazard)
- **现象**：静态分析脚本报告 `_player.css` 中的 `.tm-webdav-*` 和 `.tm-about-*` 选择器在某些组件中未出现，险些被当成“死代码”批量删除。
- **根因**：
  - 虽然设置面板主体已经重构为现代的 `AppleCard` 系统，但 `CloudSyncSection.js` 和 `AboutSection.js` 内部依然通过私有方法（`_createWebDavSyncCard`、`_createAboutCard`）动态装配了旧版 WebDAV 卡片与关于卡片。
- **最佳实践**：
  - 严禁仅凭单次正则扫描结果就盲目对 CSS 进行“一刀切”删除；
  - 必须由 Subagent 结合 AST 引用链与 DOM 实例化工厂进行运行时真实验证，确认真正 100% 零引用的规则才予以删除。

### 4. Userscript 宿主轨与 Shadow 轨双轨分离的内存红利
- **反思**：在油猴脚本中，很多开发者习惯在 `index.js` 直接 `import './style.css'`。这会导致打包器（如 Webpack 的 `style-loader`）将整整几千行 CSS 插入宿主页面的 `<head>`，而播放器内部 Shadow DOM 又解析了一遍。
- **最佳实践**：
  - 采用 **双轨分层拓扑**：
    - **宿主轨 (`_host.css`)**：仅包含唤醒浮动按钮、body 状态类和自定义根节点声明，严格限制在 `< 3 KB`；
    - **Shadow 轨 (`style.css?inline`)**：所有复杂 UI 组件 100% 封装在 Shadow DOM 内部；
  - 宿主端免去了 150KB 样式的双重解析，且彻底阻断了任何类名冲突对宿主网站的污染。
