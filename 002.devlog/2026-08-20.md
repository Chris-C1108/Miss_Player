# 开发日记 — 2026年8月20日

## 跨站点纯净模态播放器 POC 攻坚战（7mmtv.sx / Jav.sb / SupJav.com）

---

## 1. 核心任务与架构攻坚概览

### 1.1 核心目标
针对多类成人视频站（**7mmtv.sx**, **Jav.sb**, **SupJav.com**）复杂的反调试、多重嵌套 iframe、动态鉴权签名、CDN 防盗链与片头缺失（404）等问题，设计并验证一个集「**穿透抓流 + 跨沙箱二进制桥接 + 自动起播 + 纯净模态 UI**」于一体的油猴全能播放器 POC。

### 1.2 跨沙箱架构突破（Hybrid Bridge Loader）
* **演进背景**：
  * **v0.8.0 阶段**：沙箱内部定义的 Loader 无法被页面主上下文的 Hls.js 调用，触发跨域 `fragLoadError`。
  * **v0.9.0 阶段**：若将 Hls.js 运行在沙箱内部，其创建的 `MediaSource` 无法跨沙箱绑定到页面主上下文的 `<video>` 标签，导致播放完全静默。
* **架构解法（Hybrid GM Bridge）**：
  1. **页面上下文运行 Hls.js**：直接与主 DOM `<video>` 绑定，零 MSE 跨域隔离阻碍；
  2. **注入轻量 `__MissPlayerLoader`**：在页面上下文继承 `Hls.DefaultConfig.loader`，拦截 M3U8 列表和分片（TS/M4S/JPG）请求；
  3. **沙箱底层 `unsafeWindow.__mpBridge`**：通过 `GM_xmlhttpRequest` 绕过 CORS，突破防盗链并携带特定的 `Referer` / `Origin` / `User-Agent`，在沙箱内将二进制转为 Blob URL，通过轻量 `fetch(blobUrl).arrayBuffer()` 交付给 Hls.js 解复用。

## 3. 核心踩坑教训与实战经验总结

### 3.1 【踩坑 1】CDN 切片 404 缺失导致 Hls.js 陷入无限重试死锁
* **现象**：
  Jav.sb 的 CDN 节点经常缺失前几个片头分片（`index0.jpg`, `index1.jpg` 返回 404），而真实正片从 `index2.jpg`（11.4s）开始。
* **教训**：
  * 若在 Loader 层面返回 `onError(404)`，Hls.js 状态机会反复重试该缺失切片，并在重试耗尽后抛出 `fatal: true` 致命网络错误停止缓冲；
  * 若在 Loader 层面静默返回 `0 字节空文件` 或 `188 字节 TS 空包`，Hls.js 的 TS 解复用器会因缺乏视频关键帧/PES 头而抛出 `fragParsingError fatal: true`。
* **终极避坑经验**：
  * **在解析 M3U8 阶段进行「列表预净化（Pre-Sanitization）」**：在将播放列表交给 Hls.js 前，先并发向 CDN 探测前 5 个切片的可用性，直接从 M3U8 文本中**物理剔除返回 404 的切片行与 `#EXTINF` 行**。
  * Hls.js 接收到的第一帧即为 100% 真实有效的首帧视频，0 报错、0 重试、瞬间秒开！

### 3.2 【踩坑 2】Google Drive / lh3 CDN 携带 Referer 触发 429 Too Many Requests
* **现象**：
  SupJav 穿透 TurboVid 后获取到 `https://lh3.googleusercontent.com/d/{ID}=d` 视频切片，但直接请求全部返回 HTTP 429。
* **教训**：
  * Google CDN 对携带第三方网站 `Referer`（如 `https://supjav.com/...`）的跨域请求施加了极其严格的访问频控（429 Rate Limiting）。
* **终极避坑经验**：
  * 请求 Google Drive / `lh3.googleusercontent.com` 时，**严禁携带 Referer 头**，仅提供 `Origin: https://turbovidhls.com`，状态码即可瞬间恢复 200 OK。

### 3.3 【踩坑 3】页面严苛 CSP 策略拦截 Blob URL Web Worker
* **现象**：
  SupJav 页面控制台出现：`Creating a worker from 'blob:<URL>' violates the following Content Security Policy directive: "script-src 'unsafe-inline' 'unsafe-eval'..."`，导致后续解复用管道崩溃。
* **教训**：
  * Hls.js 默认开启 `enableWorker: true`，会尝试将解复用器打包为 Blob URL 并启动 Worker。在配置了严苛 CSP 的宿主网站上，该行为会被浏览器直接阻止。
* **终极避坑经验**：
  * 在 Userscript 环境初始化 Hls.js 时，建议显式配置 `enableWorker: false`，强制在主线程执行轻量级同步解复用，彻底规避宿主页面的 CSP 阻断。

### 3.4 【踩坑 4】Hls.js 1.5.x 规范对 Loader stats 结构的严格校验
* **现象**：
  自定义 Loader 回调时报 `playlist-loader.ts:317 Cannot set properties of undefined (setting 'start')`。
* **教训**：
  * Hls.js v1.5+ 对 `loader.stats` 做了深度结构重构，必须包含嵌套对象：`loading: { start, first, end }`, `parsing: { start, end }`, `buffering: { start, first, end }`。缺失任意一层都会导致 Hls.js 内部崩溃。
* **终极避坑经验**：
  * 在所有自定义 Loader 中统一使用 `createHlsStats()` 工厂函数构造完整 stats 结构。

### 3.5 【踩坑 5】多 Iframe 异步探测引起的实例争抢与 AbortError
* **现象**：
  网站包含多个广告与视频 iframe，`setInterval` 轮询会导致播放器刚刚起播就被下一个 iframe 的解析结果覆盖摧毁（`AbortError`）。
* **终极避坑经验**：
  * 一旦有任何一个 iframe 成功解析出可用视频源，立即设置 `hasExtractedSuccessfully = true` 互斥锁，并立刻注销 `scanInterval` 定时器。
