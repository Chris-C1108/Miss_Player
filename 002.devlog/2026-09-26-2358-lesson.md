## 1. 油猴脚本性能测试的“沙箱真实性”反模式

### 踩坑背景
在早期规划中，容易直觉性地照搬传统 Web 前端单页应用的自动化方案（如 Playwright 无头实例 + CDP Tracing）。但在油猴场景下直接遭遇无法运行的死胡同。

### 技术本质剖析
- **API 缺失**：Playwright 启动的干净 Chromium 并不具备 Tampermonkey / Violentmonkey 扩展沙箱，所有 `GM_*` 扩展特权 API 全部报未定义。
- **环境失真**：纯 Mock 或 `page.addInitScript` 无法真实还原油猴特有的 `Isolated World`（扩展隔离作用域）与宿主全局作用域通信开销。

### 最佳解决方案 (Standard Practice)
- **CI 门禁层**：使用最小静态页面 + 规范 GM 桩函数的隔离实例（`tests/perf/run-perf.js`），保证无依赖全自动执行。
- **业务验证层**：通过 WebSocket 原生对接本机正在运行的真实 Chrome 调试端口（`9222`）或借助专用 MCP 扩展直连目标页面执行真实上下文求值。

## 2. “空闲预构建 (requestIdleCallback)”对首屏 DOM 树的隐形污染

### 踩坑背景
直觉上为了提高菜单点击的即时性，通常会在 `startScript` 后通过 `requestIdleCallback` 悄悄把庞大的设置面板 DOM 结构先创建好隐藏在后台。

### 技术本质剖析
- 宿主视频网站（如 MissAV / Jable）页面本身已有 1,500 ~ 2,500 个复杂节点。
- 提前将未展开的 380+ 个设置子节点、表单输入框、卡片塞入 DOM 树，会导致宿主页面每一次的窗口尺寸变动、视频全屏切换或 `visualViewport` 键盘弹起时，浏览器渲染引擎都必须对所有隐藏节点执行重排计算（Layout Tree 遍历）。

### 最佳解决方案 (Standard Practice)
- 非首屏高频交互组件（设置菜单、历史日志抽屉等）**严禁任何形式的预渲染**。
- 坚决贯彻“真·按需创建”：用户不点击齿轮，DOM 节点数为 0；用户点击后，哪怕花费 10~20ms 动态构建，对用户手感而言依旧极其丝滑，且彻底解放了首屏与播放期间的渲染引擎负担。
