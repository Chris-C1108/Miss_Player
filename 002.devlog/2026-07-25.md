# 开发日记 — 2026年7月25日

## 1. 核心需求与功能更新

### 1.1 高分辨率屏幕（1080p/2K/4K）下视频画面溢出与放大修复
* **问题现象**：
  * 在 PC 高分辨率大屏或视口受限的环境下，播放器 `<div class="tm-video-container">` 被硬编码赋予了类似 `style="min-height: 1080px;"` 的内联样式，导致视频画面尺寸超出父级遮罩容器（`80vh`），画面被异常放大且溢出屏幕。
* **根因定位**：
  * `UIManager.js` 中的 `createOverlayAndContainer()` 与 `updateContainerMinHeight()` 之前直接使用 `window.innerWidth * (9/16)` 动态计算最小高度。
  * 当 screen.width = 1920px 时，算出的 `minHeight` 为 `1080px`；在 2K 屏上甚至高达 `1440px`。
* **修复逻辑**：
  * 在 `UIManager.js` 与 `DragManager.js` 的所有动态高度与 `minHeight` 计算点，增加 `Math.min(..., window.innerHeight * 0.8)` 80vh 视口高度上限约束。
  * 确保内联写入 DOM 的 `minHeight` 与 `height` 绝对不会突破容器的 80vh 视口阈值。

### 1.2 代码库冗余与内联样式精简审计 (`/ponytail-audit`)
* **架构/样式审计成果**：
  * 清理 `UIManager.js` 与 `DragManager.js` 中的无约束像素高宽硬编码。
  * 识别并规划了 `TikTokMode.ts` 与 `UIManager.js` 中内联 `style.cssText` 向 CSS 变量和纯 `.css` 样式表的收拢归纳。

## 2. 踩坑教训与避坑经验

### 2.1 CSS 规范中 `min-height` 覆盖 `max-height` 的渲染特性
* **坑点**：
  * 样式表中明确写有 `.tm-video-container { max-height: 80vh; }`，但开发者误以为设置 `max-height` 就能兜底约束所有情况。
  * 根据 W3C CSS 规范，**当元素的 `min-height` 大于 `max-height` 时，`min-height` 拥有绝对优先渲染权**，会直接无视 `max-height` 的限制。加上 JS 直接将 1080px 写在元素 HTML `style="..."` 属性上，导致 `80vh` 完全失效。
* **避坑经验**：
  * 切忌依赖 `max-height` 去强行约束一个内联带有巨大 `min-height` 的 DOM 节点。
  * 在任何通过 JavaScript 动态计算并设置内联 `min-height` / `height` 的场景下，**必须在 JS 计算阶段就施加视口相对值（如 `window.innerHeight * 0.8`）的防御性截断（Clamping）**。

### 2.2 响应式计算避免单一以 `innerWidth` 为基准
* **坑点**：
  * 原代码假设移动端竖屏宽高比固定（`16:9`），直接用 `innerWidth * 9/16`。在桌面端宽屏设备（1920x1080、2560x1440）上，`innerWidth` 极宽，乘出来的数值远超屏幕纵向总高度。
* **避坑经验**：
  * 在 Userscript 适配宿主网站时，必须时刻区分移动端与 PC 端桌面大屏环境。
  * 涉及到基于宽度的比例推算（`innerWidth * aspect`）时，必须用 `Math.min(calculatedValue, maxViewportHeight)` 进行二次封顶。
