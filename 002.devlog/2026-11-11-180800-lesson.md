# 经验教训沉淀 (Lesson Learned) - 2026-11-11-180800

## 1. 方案 A 工业级版本模型落地 (MAJOR.MINOR.PATCH-beta.XXX)

### 🚨 历史设计认知复盘
针对版本号格式 `v5.7.[递增数值]-[类型字符]` 的分析：
1. **纯类型字符缺少自增序列**（如 `5.7.115-beta`）会导致多次连续提交间版本号完全一致，`compareVersions` 结果恒为 0，移动端检查不到更新；
2. **ASCII 字典序导致认知反转**：SemVer 2.0.0 规定字符串按 ASCII 比对，导致 `'dev' (100) > 'beta' (98)`，即从 dev 转为 beta 会被误判为降级；
3. **最核心死穴**：无论预发布后缀是什么，同主版本号下的正式版优先级必然高于预发布版（`5.7.115 > 5.7.115-beta`）。

## 2. 最终确立的方案 A 工业级标准模型

全生命周期严格遵循以下链条：
$$\Large\mathbf{v5.7.[下一个目标正式版]-[类型].[三位递增序号]}$$

1. **测试版基准**：主版本号必须为下一个目标正式版（如当前正式版为 `5.7.115`，下一轮开发测试版从 `5.7.116-beta.001` 开始）；
2. **测试日常迭代**：执行 `npm run bump` 自动自增补丁序号（`5.7.116-beta.002` ➔ `5.7.116-beta.003`）；
3. **正式发版转正**：执行 `npm run bump:release`，自动剥离后缀收敛为正式版 `5.7.116`；
4. **开启下一轮测试**：正式发版后执行 `npm run bump` 自动开启 `5.7.117-beta.001`；
5. **生命周期单调递增**：`5.7.115 < 5.7.116-beta.001 < 5.7.116-beta.002 < 5.7.116 < 5.7.117-beta.001`。
