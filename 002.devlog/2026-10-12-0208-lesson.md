## 🎯 核心问题与设计反思

### 1. WebKit/Blink 引擎单边边框与圆角结合的“两端消失陷阱” (Single-Border Radius Clipping Bug)
- **现象**：给带有 `border-top-left-radius: 20px; border-top-right-radius: 20px;` 的容器设置 `border-top: 1px solid #ffffff29`，但左右下边框为 0（none）时，顶部 1px 线在左右 20px 圆角处会突然衰减消失，且视觉上给人一种“多出 1px 被父级 overflow 裁切”的错觉。
- **根因**：
  1. 默认 `background-clip: border-box` 会把深色实体背景绘制到边框外缘，半透明的浅色边框与深色底混合后反差极其微弱；
  2. WebKit 描边管线在处理未闭合单边圆角边框时，圆弧部分的线宽会沿法线迅速插值衰减为 0；
  3. 加上 `border-top` 与 `box-shadow` 双重叠加时视觉粗重繁复，严重破坏了 Apple 设计的通透感。
- **最佳实践**：
  - **在圆角卡片/底部抽屉上实现顶部 1px 微光分界线时，永远优先使用内阴影方案**：`box-shadow: inset 0 1px 0 0 rgba(255, 255, 255, 0.18)`！
  - 内阴影完全沿圆角平滑延展，且 100% 绘制在内容盒内，绝无物理外溢，永远不受父级 `overflow: hidden` 的裁切影响。同理，胶囊指示器 (`mp-switcher-indicator`) 也应完全收敛为内阴影方案。

### 2. DOM 子节点挂载次序与 Flex 主轴方向的物理映射陷阱
- **现象**：手势向左滑（Swipe Left）本应进入“左手模式（面板靠左，Gutter 靠右）”，实测却面板靠右；向右滑反而面板靠左。
- **根因**：
  - 在 JS 组装 DOM 时，主控制栏 `.tm-control-buttons` 先行挂载（child 1），单手立柱 `.tm-single-hand-gutter` 后续挂载（child 2）；
  - 当在右手模式下配置 `flex-direction: row` 时，正向排列使得 child 1 在最左侧、child 2 在最右侧，导致右手模式反而在屏幕左侧显示面板！
- **最佳实践**：
  - 遇到 flex 镜像对齐需求时，必须先行打印或核实 DOM 树物理挂载先后；
  - 本项目中 child 1 为主面板、child 2 为 Gutter：
    - **左手模式**（主面板在左）必须使用 `flex-direction: row`；
    - **右手模式**（主面板在右）必须使用 `flex-direction: row-reverse`。

### 3. 多层交互界面的事件击穿与滑动动态让位设计
- **反思**：在原有的单层 Flex 结构中，播放状态切换器 Switcher 被音量按键与倍速按键卡在中间，宽度仅剩 200px 左右，在单手 320px 宽度下极其逼仄，且滑动误触率极高。
- **最佳实践**：
  - 采用现代 Apple 控件（如动态岛/控制中心）的“**双层叠加架构**”：
    - 底层全宽展开（width: 100%），触摸感知面积扩大至整个行；
    - 上层设置 `pointer-events: none` 容器，左右按键容器恢复 `pointer-events: auto`；
    - 在底层开始拖动瞬间（`isDragging`），由上层按键执行 `translateX(±120%)` 硬件加速退出动画，为底层滑动彻底腾出舞台；松手吸附后优雅滑回。

### 4. 物理滑块步进越级跳跃的边界防线
- **陷阱**：在物理动量计算（velocity + projectedDeltaX）时，如果允许 `step = Math.min(2, ...)`，用户稍加用力就会直接跳过中间档位（例如从“快速预览”瞬间滑到“精彩重温”）。
- **最佳实践**：
  - 状态档位切换器必须具有明确的档位认知模型：每次滑动必须且只能移动 1 个档位；
  - 必须实施**双重边界守卫**：
    1. 实时拖拽阶段，将履带物理位移限制在 `[currentIndex - 1, currentIndex + 1]` 的物理坐标区间；
    2. 松手释放阶段，步长只能为 `±1`（`step = Math.sign(...)`），从根本上杜绝跨档位跳动。
