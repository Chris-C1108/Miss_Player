## 🚫 核心反模式禁令清单 (Forbidden vs Use)

### 1. 探测函数假阴性吞噬网络与权限异常
* **病灶现象**：`checkDirectoryExists()` 中简单粗暴写 `catch (err) { return false; }`。当遇上公网域名超时断连（无 NAT 回流）或 401 密码错误时，函数假装“目录不存在”，进而驱动上层执行 `MKCOL`，最后把底层真正的原因篡改为业务级报错 `目录无法自动创建`，从而彻底骗过故障转移拦截网 (`_isNetworkError`)，导致备用端点完全没机会上场。
* **FORBIDDEN**：`async checkExists() { try { ... } catch { return false; } }`（把网络连接失败或 401 伪装成“不存在”）。
* **USE**：**状态语义严格分层**——只有服务端明确响应的 `404` / `409` / `410` 才算“物理不存在（返回 false）”；任何超时、TCP 断连、CORS 或 `401/403` 鉴权错误必须原样抛出，让上层 `executeWithFailover` 决策重试或快速提示。

### 2. 分散的业务入口校验导致“功能孤岛”
* **病灶现象**：项目中同时存在云同步、热度图、评论、STRM 入库、疯狂采集、调试日志等 15 个依赖 WebDAV 的模块，各模块各自手写 `if (!config.url)` 校验逻辑。当引入新特性（如备用地址 `lanUrl`）或仅填写内网地址时，局部打补丁必然漏掉边缘模块。
* **FORBIDDEN**：在各业务组件中直接写死 `if (!config || !config.url)` 散装判定。
* **USE**：**架构级单一信源 (Single Source of Truth)**——在 `WebDavClient` 上下沉封装全局唯一准入校验函数 `WebDavClient.hasValidEndpoint(config)`，全项目 15 个业务入口强制统一调用。

### 3. 盲目为所有裸主机名拼接 `https://`
* **病灶现象**：当用户习惯性填入纯内网地址 `192.168.2.250:5005`（未带协议头）时，原代码无脑补充 `https://`，结果大多数局域网 NAS WebDAV 服务仅监听 HTTP 端口，引发致命的 SSL 握手断连。
* **FORBIDDEN**：`if (!/^https?:\/\//i.test(url)) url = 'https://' + url;`
* **USE**：区分私网与公网域名（`isPrivateNetworkHost` 识别 `192.168.*`、`10.*`、`172.16-31.*`、`localhost`、`.local`），私网默认补 `http://`，公网默认补 `https://`。

### 4. 过度信任移动端 Userscript `GM_xmlhttpRequest` 的原生 `ontimeout`
* **病灶现象**：在 iOS/macOS Safari Stay 等移动端管理器中，向不可达的内网/回流受阻公网发起请求时，底层 `ontimeout` 时常卡死不触发或 `status` 返回 `0`。
* **FORBIDDEN**：仅依赖 `GM_xmlhttpRequest` 传入的 `timeout` 配置而不做外部兜底。
* **USE**：外层加装 `timeout + 400ms` 的 JS 级硬熔断定时器 (`setTimeout`) 确保在预定时间坚决拒绝 Promise；同时显式捕获 `status === 0` 并作为核心网络故障信号。
