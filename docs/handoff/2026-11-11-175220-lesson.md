# 经验教训沉淀 (Lesson Learned) - 2026-11-11-175220

## 1. 致命缺陷：SemVer 2.0.0 规范下预发布测试版与同名正式版的优先级错位 (Pre-release vs Release Priority Inversion)

### 🚨 现场还原与反模式
在之前的日常开发提交中，出现过以下版本流转现象：
1. 客户端已安装或缓存了 `5.7.115`（正式版格式）；
2. 随后向 GitHub main 分支推送了 `5.7.115-001`（试图作为 5.7.115 的第 1 个补丁测试版）；
3. **严重后果 1**：客户端处于 `v5.7.115` 时点击“检查更新”，比对引擎依据严格的 SemVer 2.0.0 规范执行：
   - 核心版本三段号相同（`5.7.115` vs `5.7.115`）；
   - 正式版本优先级严格高于预发布版本（`5.7.115 > 5.7.115-001`）；
   - 比对引擎判定远程版本比本地更低（`hasUpdate = false`），客户端显示“当前已是最新”，检查不到更新！
4. **严重后果 2**：用户感到疑惑并手动点击一键安装了 `v5.7.115-001`，安装完成后终端版本变为 `v5.7.115-001`；
   - 此时客户端检查更新或从缓存中读取到之前的 `v5.7.115`；
   - 比对引擎再次判定 `5.7.115 > 5.7.115-001`；
   - 界面弹出：`☆ 发现新版本 v5.7.115，当前安装为 v5.7.115-001`，导致刚装完最新测试版却立刻收到升级到旧版本的荒谬提示！

---

## 2. 核心架构认知与禁令

- **FORBIDDEN: 严禁在已存在或已发布正式版 `A.B.C` 后，发布同名预发布版本 `A.B.C-xxx`**；
- **USE: 预发布测试版必须是“下一个正式版的前序基准”，版本必须保持单调严格递增**：
  1. 当前正式版为 `A.B.C`（如 `5.7.115`）；
  2. 新一轮开发测试版必须以 `A.B.(C+1)-001`（如 `5.7.116-001`）为起点，确保 `5.7.116-001 > 5.7.115`；
  3. 日常测试迭代执行 `npm run bump` 自增后缀（`5.7.116-002` ➔ `5.7.116-003`）；
  4. 正式发版时执行 `npm run bump:release`，自动剥离后缀收敛为正式版 `5.7.116`；
  5. 整个生命周期完全单调递增：`5.7.115 < 5.7.116-001 < 5.7.116-002 < 5.7.116`。

---

## 3. 防倒退工程化防线 (Anti-regression Defense in bump script)

在 `scripts/bump-version.js` 中内置了 SemVer 2.0.0 防倒退卫兵校验：
- 当试图执行版本号修改时，自动执行 `compareVersions(targetVersion, oldVersion)`；
- 一旦目标版本小于或等于当前版本，立即中断并报错退出（`process.exit(1)`），从构建源头彻底杜绝版本语义倒退。
