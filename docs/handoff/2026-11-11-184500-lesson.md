## 🚨 核心教训与反模式禁令

### 1. 编译期 Userscript Header 目标分支决议：以版本语义为主，绝不单纯依赖 Git 当前分支
* **反模式 (FORBIDDEN)**：
  `FORBIDDEN: const gitBranch = execSync('git rev-parse --abbrev-ref HEAD').trim();`
  - **严重后果**：开发者日常工作区常驻在 `dev` 分支，执行 `npm run bump:release` 将版本号收敛为正式版（如 `5.7.117`）并构建时，由于当前分支是 `dev`，打包器会将 `@updateURL` 错误注入为 `.../dev/dist/miss_player.meta.js`。当该构建产物通过镜像直推到 `main` 分支发布给 SleazyFork 后，所有安装正式版的用户脚本头均指向 `dev` 分支，彻底破坏了正式版与测试版的通道隔离！
* **标准模式 (USE)**：
  `USE: const isPrerelease = String(pkg.version).includes('-'); const gitBranch = process.env.BUILD_TARGET_BRANCH || (isPrerelease ? 'dev' : 'main');`
  - **优势**：由版本号自身的语义（是否含有 prerelease 后缀）决定目标分发渠道，无论在哪个本地分支构建，正式版永远绑定 `main` 直链，测试版永远绑定 `dev` 直链。

### 2. 合规门禁 (Compliance Lint) 必须校验 Header 与版本类型的分支对应关系
* **反模式 (FORBIDDEN)**：
  `FORBIDDEN: hasValid = meta.includes('dev') || meta.includes('main');`
  - 宽松放行会导致正式版携带 dev 直链或测试版携带 main 直链逃逸到远程。
* **标准模式 (USE)**：
  `USE: const expectedBranch = pkg.version.includes('-') ? 'dev' : 'main'; assert(meta.includes(`/${expectedBranch}/dist/`));`
  - 门禁强制校验，只要发生分支错配立即阻断打包。
